# OUTDOOR RACE HUB 自動更新・デプロイ エラー対応プロセス＆再発防止ガイド

本ドキュメントでは、GitHub Actions による自動更新（毎朝8時同期）および GitHub Pages へのデプロイにおいてエラーが発生した際の**標準対応プロセス**と、実施済みの**再発防止策**をまとめています。

---

## 1. 実施済みの再発防止策（2026年11月14日適用）

2026年11月14日に発生した `Found 0 artifact(s)`（アップロード直後に GitHub Pages 側で成果物が見つからずデプロイ失敗する事象）に対し、以下の恒久対策を全ワークフロー（`deploy.yml` / `daily_sync.yml` / `auto_update.yml`）に実装しました。

1. **Pages 関連アクションの最新版への統一**
   - `actions/configure-pages@v6`、`actions/upload-pages-artifact@v5`、`actions/deploy-pages@v5` へ更新し、古い `v3`/`v4` 間の互換性・API 検出エラーを解消しました。
2. **アーティファクト反映待機ステップの追加（`sleep 10`）**
   - `Upload Artifact` 完了直後の GitHub サーバー側反映遅延を吸収するため、デプロイ前に 10 秒の待機を挟んでいます。
3. **デプロイ自動リトライ機構（最大3回）**
   - 1回目の `Deploy to GitHub Pages` が失敗した場合、**15秒待機後に自動リトライ（2回目）**、それでも失敗した場合は **30秒待機後に最終リトライ（3回目）** を自動実行します。
4. **ワークフロー間の競合キャンセル防止**
   - `deploy.yml` の `cancel-in-progress` を `false` に変更し、`daily_sync.yml` の自動同期コミット（`chore(auto):`）による重複トリガーを除外することで、実行中のデプロイが途中で強制終了される事故を防止しました。
5. **毎朝定期同期の3段階スケジュール（既存）**
   - `07:50 JST`（本番）、`08:40 JST`（予備1）、`10:15 JST`（予備2）の3枠が設定されており、1回目で失敗しても当日分が未完了であれば自動で再実行されます。
6. **自動診断サマリー（`GITHUB_STEP_SUMMARY`）**
   - 失敗時は GitHub Actions の Summary 画面に、どのステップで失敗したかと復旧手順が日本語で自動出力されます。

---

## 2. エラー発生時の対応プロセス

万が一、メール通知や GitHub Actions 画面でエラー（赤い `×` マーク）を確認した場合は、以下の手順で切り分け・復旧を行ってください。

### ステップ 1: 失敗箇所の確認
1. GitHub リポジトリの **「Actions」** タブを開き、赤い `×` が付いているワークフローをクリックします。
2. 画面上部の **「Summary」** に出力された診断レポート（各ステップの結果）を確認します。

### ステップ 2: 原因別の復旧手順

| 失敗したステップ | 主な原因 | 対処方法 |
| :--- | :--- | :--- |
| **Deploy to GitHub Pages**<br>（3回すべて失敗） | GitHub Pages 側の一時障害、または API 通信エラー | 1. [GitHub Status](https://www.githubstatus.com/) で `Pages` / `Actions` に障害が出ていないか確認します。<br>2. 復旧後、ワークフロー画面右上の **「Re-run all jobs」** をクリックします。 |
| **Build SPA for GitHub Pages** | データ形式不正・リンク切れ・TypeScript エラー | 1. ローカルで `npm run build` を実行し、失敗した検査項目（1〜4）や型エラーを確認します。<br>2. 該当データ（`src/data/*.json`）やコードを修正し、コミット＆プッシュします。 |
| **Step 1: 装備カタログ更新**<br>（`daily_sync.yml`） | 楽天APIの通信制限・一時エラー・商品ページ取得失敗 | 前日データへ自動ロールバックされ、サイト自体は正常公開されています。予備スケジュール（08:40 / 10:15）で自動再実行されるため、通常は静観で問題ありません。 |
| **Step 2: 大会データ更新**<br>（`daily_sync.yml`） | Gemini API の一時エラーや対象サイトのタイムアウト | 同上（前日データで保護・自動再実行）。連続して失敗する場合は `GEMINI_API_KEY` の有効期限やクォータを確認してください。 |
| **Step 3: スプレッドシート同期**<br>（`daily_sync.yml`） | Google API 認証エラー・スプレッドシート権限変更 | `GCP_SA_KEY` の有効性、およびスプレッドシートの共有設定（サービスアカウントが「編集者」になっているか）を確認してください。 |
| **Step 6: Gitコミット＆プッシュ**<br>（`daily_sync.yml`） | 同時刻の手動プッシュとの競合 | 3回自動リトライ後も失敗した場合のみ発生します。Actions の「Re-run all jobs」を実行してください。 |

### ステップ 3: 緊急時の手動デプロイ手順
GitHub Actions の特定ジョブを再実行したい場合：
1. GitHub リポジトリの **「Actions」** タブ ＞ 左メニューの **「Deploy to GitHub Pages」** を開きます。
2. 右上の **「Run workflow」** ＞ ブランチ `main` を選択 ＞ 緑色の **「Run workflow」** ボタンを押します。
3. 完了後、サイト画面右上の「最新情報」日時が更新されていることを確認します（ブラウザキャッシュが残る場合は `Ctrl + F5` でスーパーリロードしてください）。
